# The runtime bundle

The runtime bundle is the pinned archive of Bionic and ART that every app
process runs on top of (ADR-0010). This document records what the bundle turned
out to contain and how it is produced, with the commands that established it,
so later phases start from evidence instead of from the design sketches.

Everything below runs against the system image the retired container port had
already downloaded, `/var/lib/mosaic/images/system.img`, using only `debugfs`.
No root, no loop mount, no container, no kernel module.

## Producing one

```
tools/bundle/bundle.sh build <system-image> <bundle-dir>
```

That produces a self-contained directory: the Android linker, 47 shared
libraries, the boot classpath jars, ICU data, a linker configuration, and
`env.sh` / `run.sh` that set up the environment a Bionic process expects.

```
tools/bundle/bundle.sh run <bundle-dir> dalvikvm64 -XXlib:<bundle>/lib64/libart.so -showversion
ART version 2.1.0 x86_64
```

## What it contains

| Piece | Where it came from |
| --- | --- |
| `linker64`, also `lib64/ld-android.so` | `/system/apex/com.android.runtime/bin/linker64` |
| Bionic (`libc.so`, `libm.so`, `libdl.so`, `libdl_android.so`) | `/system/apex/com.android.runtime/lib64/bionic/` |
| ART (`libart.so`, `libartbase.so`, `libdexfile.so`, …) | `/system/apex/com.android.art/lib64/` |
| `libandroid.so` and the rest of the preload list | `/system/lib64/`, the apexes |
| Boot classpath jars | `/system/apex/com.android.art/javalib/`, the i18n apex, `/system/framework/` |
| `etc/public.libraries.txt` | `/system/etc/`, the list ART preloads |
| ICU data (`icudt70l.dat`) | `/system/apex/com.android.i18n/etc/icu/` |
| `ld.config.txt`, `env.sh` | generated by the bundle tool |

The library set is the *closure* of the linker, ART, and the preload list: 47
libraries, discovered rather than listed.

## The gate: a DEX runs

```
tools/bundle/with-logd.sh <bundle>/run.sh dalvikvm64 \
  -XXlib:<bundle>/lib64/libart.so \
  -Xbootclasspath:"$(cat <bundle>/bootclasspath.txt)" \
  -cp am.jar com.android.commands.am.Am
```

`am` is a real Android command-line tool. It starts, initialises the framework
classes, and fails only where it needs a JNI method that `libandroid_runtime.so`
would register:

```
No implementation found for boolean android.os.SystemProperties.native_get_boolean(...)
  at android.os.SystemProperties.native_get_boolean(Native Method)
  at android.os.SystemProperties.getBoolean(SystemProperties.java:215)
  at android.app.ActivityManager.<clinit>(ActivityManager.java:928)
  at android.app.ActivityManager.getService(ActivityManager.java:4693)
  at com.android.commands.am.Am.svcInit() (Am.java:58)
  at com.android.commands.am.Am.main(java.lang.String[]) (Am.java:54)
Exception in thread "main" java.lang.UnsatisfiedLinkError: ...
```

That is DEX bytecode executing on ART, in a host process, with no Android OS
booted. The failure is at the framework boundary, which is Phase 2, not at the
execution model.

## What was hard, and why

Five things cost real time. All five are encoded in the tool so they are paid
for once.

**`/system/lib64` is mostly symlinks into the apexes.** Dumping a symlink
produces a zero-byte file that the linker reports as
`file offset for the library "libc.so" >= file size: 0 >= 0`. Only real files
are staged, and the index records which is which.

**A `dlopen` failure can be silent.** `libart.so` is `dlopen`ed and needs twenty
other libraries; the linker named none of them. Walking `DT_NEEDED` with
`readelf` finds those gaps first, which is the difference between one command
and twenty rounds of guessing.

**The namespace holding libc.so must be the one ART looks up by name.** This is
the one that took longest, and the fix is three lines of configuration. The
linker creates the process's namespaces at startup from the section matching the
executable. Declaring a *separate* namespace named `system` looks equivalent and
is not: ART's classloader namespace then becomes a child of that empty
namespace, so every later `dlopen` loads a second copy of `libc.so`, which
bionic refuses because libc uses initial-exec TLS:

```
dlopen failed: TLS symbol "(null)" in dlopened ".../lib64/libc.so" ... using IE access model
```

The fix is one section covering the whole bundle, its default namespace made
visible, which is what `bundle.sh` writes. `visible = true` is the key that
exports a namespace to `android_get_exported_namespace`; there is no
`is_exported` key, and the linker's own strings are the only documentation.

**A Bionic process expects `init`'s environment.** `ANDROID_ROOT`,
`ANDROID_DATA`, `ANDROID_ART_ROOT`, `ANDROID_I18N_ROOT`, `ANDROID_TZDATA_ROOT`,
`ANDROID_TMP`. Without `ANDROID_ROOT` ART cannot find its configuration; without
`ANDROID_DATA` it has nowhere to write `dalvik-cache`. The bundle carries them in
`env.sh`.

**ART needs more than libraries.** The boot classpath jars, the ICU data file
that ART opens by name, and `etc/public.libraries.txt`, which libnativeloader
reads and aborts on if it is missing.

## Debugging a Bionic process

A Bionic process logs through liblog, which sends datagrams to
`/dev/socket/logdw` and **drops them when nothing is listening**. That is why an
Android process on a Linux host aborts with no explanation, and why
`Fatal signal 6` is often all you get.

```
tools/bundle/with-logd.sh <command> [args...]
```

runs the command with a private `/dev` and a minimal logd, which turns ART's
output into readable text — including the symbolised native backtraces that
identified `libnativeloader::LibraryNamespaces::Initialize` as the preload
abort, and the linker's own view of the world. It needs no root.

## Known gaps

- The JIT is not exercised. ART reports it cannot load `libart-compiler.so`
  unless the bundle carries it; the bundle now does, but nothing depends on it
  yet.
- The boot classpath is hand-listed in `bundle.sh` rather than derived from the
  image's build configuration. A different image will need a different list.
- Nothing here is packaged as a pinned archive yet (ADR-0010). The bundle is
  built locally from an image; publishing it is still to do.

## Phase 2: an app process runs

`app_process64` is the entry point a device uses: it loads `libandroid_runtime.so`
and starts the framework. It now starts, registers its JNI natives, initialises
`Build.VERSION` and `RuntimeInit`, and runs `am` until it needs Binder:

```
AndroidRuntime: >>>>>> START com.android.internal.os.RuntimeInit uid 0 <<<<<<
...
  at android.os.ServiceManager.getIServiceManager(ServiceManager.java:129)
  at android.os.ServiceManager.rawGetService(ServiceManager.java:372)
  at android.os.ServiceManager.getService(ServiceManager.java:147)
  at android.app.ActivityManager.getService(ActivityManager.java:4693)
```

That is the Phase 3 boundary, not a problem with the execution model.

Two things were missing to get here, and both are the same shape: something
`init` provides on a device that has no equivalent on a host.

### System properties

ART and `app_process` read properties throughout startup, and Bionic reads them
from a mapped area at `/dev/__properties__` rather than from a daemon. Without
it, every property is empty and `app_process` stops at
`Unable to determine ABI list from property ro.product.cpu.abilist64`.

`tools/bundle/make-property-area.py` generates that area. It implements both
formats from AOSP: the `property_info` trie that maps a name to a context, and
the `prop_area` shared memory that holds the values, with the trie of `prop_bt`
nodes whose siblings are a binary search tree ordered by (length, bytes). The
trie it writes is deliberately minimal — one root node with no children and one
exact match per property, which the reader accepts because it breaks out of its
descent when a node has no children.

`bundle.sh build` runs it into `<bundle>/properties`, seeded from the image's
`build.prop`, so the bundle carries the area the privileged step installs
(ADR-0013). Verified with a property-reading binary from the image:

```
$ getprop ro.build.version.sdk
33
$ getprop ro.product.cpu.abilist64
x86_64
```

### A working logd

Covered above: without one, a Bionic process aborts with no explanation. It is
also how the two remaining property gaps were found — `Build.VERSION`
dereferences `ALL_CODENAMES[0]` before checking its length, so an empty list
aborts the framework's static initialisation, and that is only visible in a log.
